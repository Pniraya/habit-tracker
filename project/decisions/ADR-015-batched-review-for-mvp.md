# ADR-015: 评审批量后置，先交付 MVP

- 状态：`ACCEPTED`
- 日期：`2026-11-05`
- 决策者：用户（本轮明确选择「立 ADR-015：评审批量后置」，见「用户授权来源」）
- 关联：`ADR-012`（稳定 main）、`ADR-013`（评审证据）、`ADR-014`（单一验证入口）、`AGENTS.md` §5/§7/§12

## 背景

截至 `TASK-025`，每个任务都走「独立评审 → `APPROVE` → 合入 `main`」的完整流程。仅 `TASK-025` 一个 spike 任务就消耗了 3 轮评审、4 条阻断，而阻断全部是文档口径问题，没有一条是代码缺陷。

这个流程在交付功能之外还交付了两样东西：可核对的历史，以及真实的返工证据。但它有一个可量化的代价——**评审往返约 3 倍于实现时间**，且评审自身的发现率随任务粒度变小而下降（`TASK-025` 三轮都在审文字）。

用户的目标变了：先要一份**可用的 MVP**，评审攒到项目完成后一次做完。

## 决策

1. 新增任务状态 `IMPLEMENTED`（实现完成，待批审）。语义：代码与自测已完成，**未经独立评审**。

2. `main` 允许合入 `IMPLEMENTED` 的任务，条件是：
   - `tools/verify-all.ps1` 通过（编译、单测、DAO、diff、治理）；
   - 该任务在 `project/PROJECT_STATUS.md` 的「待批审清单」里逐条登记。

3. `DONE` 的含义**不变**：仍然要求独立 Reviewer 的 `APPROVE` 记录。批量评审通过后，任务由 `IMPLEMENTED` 转 `DONE`，并从待批审清单移除。

4. `check-governance.ps1` 第 18 项扩写（**不新增检查项，总数仍为 22**）：
   - `DONE` 任务：必须有 `INDEPENDENT` + `APPROVE` 记录（原规则，未放宽）；
   - `IMPLEMENTED` 任务：必须出现在待批审清单，否则 FAIL；
   - 待批审清单里不得留下已 `DONE` 或状态不存在的条目（防清单腐烂）。

5. 批量评审的入口是新增的 `project/reviews/BATCH_REVIEW.md` 模板：一次覆盖所有 `IMPLEMENTED` 任务，输出统一结论，并对每条任务写回各自的 `REVIEW-TASK-xxx.md`（因为第 18 项只认 per-task 记录）。

## 为什么不是「干脆不要评审」

用户要的是「晚点审」，不是「不审」。保留 `DONE` 必须 `APPROVE` 这条，意味着**没有任何任务可以靠改状态绕过评审**——只是评审的时点从「每任务」挪到「里程碑」。这比取消评审更安全：取消之后，「完成」和「未完成」就只剩开发者的自述。

## 受保护文件的最小改动

- `AGENTS.md` §5「完成定义」：增加 `IMPLEMENTED` 的适用条件与证据要求。
- `AGENTS.md` §7 第一条：`main` 的合入条件加入 `IMPLEMENTED` + 待批审登记。
- `AGENTS.md` §12：验证顺序末段增加批量评审时点说明。
- 未改动 `ARCHITECTURE.md`、`DATABASE.md`、`DEVELOPMENT.md`、`project/REQUIREMENTS.md`、`README_GOVERNANCE.md`。

## 被否决的方案

- **完全取消独立评审**：`TASK-021`~`TASK-024` 的评审各自抓出过真实缺陷（缺失断言、无效钳位、接口默认实现掩盖 N+1）。全部取消等于把这层保护清零。
- **把评审改成可选**：可选等于没有。要么要求，要么不要求。
- **只在分支上积累不合 main**：`main` 会长期落后于实际代码，「main 永远可构建」这条承诺变成空话，且里程碑合并时冲突会集中爆发。

## 影响与风险

- **风险：批量评审发现结构性缺陷时返工面变大**。缓解：每个 `IMPLEMENTED` 必须写「已知缺口」与「自测证据」，让评审能在不读全部代码的情况下定位风险。
- **风险：待批审清单腐烂**（任务改了状态但清单没改）。缓解：第 18 项双向校验。
- **不再有的东西**：每个任务合入前的独立确认。`IMPLEMENTED` 期间 `main` 的正确性仅由 `verify-all` 与开发者自测保证。
