# BASELINE_REVIEW.md

> 对 2026-11-04 已有 `ARCHITECTURE.md`、`DATABASE.md`、`DEVELOPMENT.md` 的静态审查。本文区分明确问题、需要澄清的产品语义和后续实现检查项。未在此处擅自修改原基线。

## 总体结论

三份文档的总体技术方向一致：Android 本地应用、单 Gradle module、Kotlin/Compose、Room、轻量分层、Normal 非精确提醒。可以作为初始设计基线，但不建议在以下问题关闭前直接实现相关业务逻辑。

## A. 必须在相关功能开发前解决

### A1. 归档时间与归档日期的口径不一致
- `DATABASE.md` 的 `habits.archived_at` 是 epoch milliseconds 时间戳。
- 连续天数/统计章节又使用“归档日期”作为有效期最后日期，并要求归档当天冻结状态。
- 若归档发生在本地午夜附近，必须明确使用哪个 `ZoneId` 将 Instant 转为 LocalDate，以及设备时区后来变化时是否重新解释。
- 建议：归档操作同时保存 `archived_at`（Instant）和明确的 `archived_local_date`（当时设备 ZoneId 下的 LocalDate），并保存/记录当时 ZoneId；是否增加字段需用户批准并建立 ADR。另一种方案是定义所有历史统计始终按当前设备时区解释，但这会改变跨时区语义。

### A2. `HabitLog.status` 与数值字段存在冗余一致性
- `status` 可由 `actual_value`、`target_snapshot` 和追踪类型推导；`completed_at` 又表达首次达标时间。
- 文档要求三者一致，但没有明确唯一写入入口、数据库层约束策略和修复策略。
- 建议：Domain 统一计算并在同一事务写入；DAO 不暴露任意字段组合更新；增加不变量测试。需要决定 status 是持久化字段还是查询时派生字段。若保留持久化字段，应明确损坏数据的检测方式。

### A3. “平均用时”没有数据来源定义
- 需求/概念稿包含平均用时，`habit_logs.duration_seconds` 是可选字段。
- 目前没有开始/结束计时、手动填写或自动测量流程，因此无法可靠计算平均用时。
- 建议：确认 V1 是否移除该指标、手动录入，或新增计时交互。未确认前将该功能标记 BLOCKED，不要生成虚假统计。

### A4. 计划版本不重叠的数据库约束
- 文档已正确指出 SQLite 普通 CHECK 不能直接表达跨行区间不重叠。
- 必须在同一事务内验证同一 habit 的日期区间无重叠，并防止并发写入造成竞态；增加边界测试（同日切换、未来生效、开区间）。
- 不能只依赖 UI 层检查。

## B. 需要统一表达或补充测试

### B1. 提醒触发后的下一次调度
- `ARCHITECTURE.md` 要求 Receiver 触发后计算并注册下一次触发。
- 需确保重复广播、迟到广播、系统时间跳变、夏令时跳变不会造成重复通知或漏掉后续提醒。
- 应使用稳定 PendingIntent 标识，并在触发时重新查询数据库；对已过期触发时间采用明确的“跳过/立即发/顺延”规则。此规则目前未定义。

### B2. 数值型习惯的撤销语义
- 文档同时支持“增量”“设置具体值”和“达标后减少到目标以下”。
- 需要定义撤销是清零、回退最近一次增量，还是手动设置新值。当前数据库只存每日汇总值，不保存操作时间轴，因此无法可靠实现“撤销最近一次增量”。
- 建议 V1 将撤销定义为显式设定当天总值，或清零；若需要逐笔撤销则需新增操作记录表，改变现有数据模型。

### B3. 目标变更与历史快照
- `target_snapshot` 可保持历史判定稳定，但需明确目标修改仅影响新日期日志，还是当天已有日志也更新快照并重算状态。
- 建议明确：已产生的历史日志快照不变；当天若尚未记录则使用新目标；当天已有记录是否更新快照需要产品确认并写测试。

### B4. 时间戳和备份格式
- 备份部分推荐 epoch milliseconds，但允许描述中出现 ISO-8601 UTC；应最终固定一种格式。当前文件推荐 epoch milliseconds，可在实现规范中将其设为唯一格式。
- 备份导入合并策略若遇到冲突需要用户选择，但具体交互未定义；这属于备份 UI 任务的前置决策。

### B5. 今日完成数分母
- 建议分母只统计当天应执行的习惯，而不是所有未归档习惯；需要在产品需求中确认后实现。

## C. 文档维护建议

1. 把本报告中的 A 类问题逐项关闭，再冻结数据库 schema。
2. 每次已批准的架构/数据/提醒决策写 ADR，并同步更新主文档。
3. 不要在开始业务编码前一次性实现所有表；先做数据库 schema 与不变量测试。
4. 对所有依赖当前时间的计算注入 `Clock`，固定时区测试。
5. `FEATURE_MATRIX.md` 的 `VERIFIED` 与 `DEVICE_VERIFIED` 分开记录，避免把编译通过误认为真机通过。

## 结论
当前文档足以启动治理初始化和 Android 工程骨架准备；数据库业务实现、统计和提醒功能应按 A 类问题关闭顺序推进。
