## 2. Q1~Q10 逐条建议

### Q1 流程：先评审，还是先做 `TASK-030`？

**结论：不，两者都不要原样执行。** 顺序为：

`TASK-026（含测试底座）` → `窄口径里程碑评审 R1` → `030a 导出` → `030b 恢复`

**理由：**
- 先做 030 会把「恢复」建在未经运行时验证的 Room 契约上。恢复要一次写入所有表并满足触发器，是最容易暴露 B3 问题的功能。
- 评审要做，但「逐任务读 diff」成本高、产出低。

**评审怎么做才不贵（R1）：**
1. 按 Q9 的「偏差表」逐项勾选：设计稿/需求 vs 现状，是否都有记录。
2. 7 个任务只读**写路径**（UseCase → 事务 → DAO）和**规则边界**（Schedule / Streak / LogStatus），UI 层只看状态流。
3. **变异抽查**：挑 3 个最关键的规则文件，人工做约 10 个变异（`<` 改 `<=`、日期 ±1、漏掉一个分支），看单测是否变红。变红的变异越少，说明 154 个单测越不可信。成本约半小时，是检验「测试是否同源自证」最便宜的办法。
4. **评审人必须是不带实现上下文的新会话（或真人）**。同一上下文里的「评审」不算 ADR-015 要求的独立评审。
5. 产出 1 份 review 记录：7 个任务一起转 `DONE`，或列出阻塞项。

**里程碑定义：** `Gate 3 出口 = TASK-026 完成 + R1 评审通过`。出口之前不开新功能，只读的 030a 除外。

**可落成任务：** `N1 TASK-026`、`N2 R1 评审（模板见上）`。

### Q2 UI 自动化路线

**结论：选 (a) 设备侧 Compose UI 测试，只做两层、≤8 个用例。不做 (b)、(c)。**

- (b) Robolectric 走 Gradle worker，大概率同样被沙箱阻断。你有真机，没必要绕。
- (c) 截图对比：没有基准库、维护成本高，推迟。

**两层切法：**

**L1 无状态屏幕测试（不碰 DB，快且稳）**：给定固定 `UiState`，断言「状态→语义树」「事件→回调参数」。
- 今日页：空态 / 部分完成 / 全部完成；点击回调；数值输入边界（空、0、小数、超大）。
- 统计 / 详情 / 我的页：关键文本、`contentDescription`、触控目标 ≥48dp（`assertTouchHeightIsAtLeast`）、月→日分组展开折叠。

**L2 真实 Room + 固定 Clock（≤3 条，每条必须断言单测够不到的东西）：**
1. 建 → 打卡 → 撤销：同时断言 DB 行和屏幕。
2. 导航参数 + `ActivityScenario.recreate()`：详情页重建后仍是同一习惯、同一周。（这正是你说的「导航参数/状态恢复零自动化」。）
3. 归档 → 恢复：今日 / 我的 / 详情三处一致。

**怎样避免变成「点一遍的脚本」：** 每个测试必须至少有一个断言，对应「出了 bug 单测不会红」的失败模式（渲染、导航、状态恢复、持久化）。删掉断言后仍能通过的，就是脚本。

**环境卫生：** 关动画（`testOptions.animationsDisabled = true`，设备开发者选项也关）；固定 Clock；每个测试用独立 DB。**先看 R1（第 3 节）再跑**，设备侧测试可能卸载 App 并清空真机数据。

**可落成任务：** `N6 UI 自动化 ≤8 用例（依赖 N1 底座）`。

### Q3 Room 契约测试（`TASK-026`）最小集

**结论：你的 4 个候选基本正确，我建议补强如下，并加 1 个可选项。**

1. **触发器/约束在真实打开路径上生效。** 用生产 `callback()` 构建 Room，满足三点：
   - 查 `sqlite_master`，断言触发器名存在（直接证明「callback 真的注册了」）。
   - 违规写入，断言抛出约束异常。
   - **关闭后重新打开**同一个文件，再违规一次，断言仍抛出。因此底座必须用临时文件 DB，不能只用内存 DB。
2. **Converter + 实体往返。** 覆盖日期（跨年、闰日 2028-02-29）、枚举、可空字段、数值日志的精度（若是 `REAL`，检查 0.1×3 类问题，需确认）。再用 `TimeZone.setDefault` 切两个时区各跑一遍，断言日期语义不漂移。
3. **`withTransaction` 原子性，用真实 UseCase 而不是玩具。** 选一个多语句写入（例如「改频率」=关闭旧版本 + 插入新版本，或「归档」），在中途注入异常，断言全部回滚。
4. **Flow 失效通知 + 无中间态。** 写入后 Flow 收到新值；更重要的是，对一个两步事务收集所有发射，断言**从未出现只完成一半的状态**。这是 Presenter 正确性的前提。
5. （可选）**外键 / 级联删除**：删习惯后日志也消失。Room 通常会开启外键，但请用测试证明，不要凭记忆。

**配套检查：**
- `exportSchema = true` 且 schema JSON 已提交。
- 确认没有 `fallbackToDestructiveMigration()`，这会静默清库。

**可落成任务：** `N1 TASK-026`（含底座：临时文件 DB、固定 Clock、造数 DSL）。

### Q4 日志窗口（不加聚合表）

**结论：把三类读取分别做成有界，并且「先量再改」。不要用「最近 90 天」窗口，也不要加缓存列。**

1. **统计页（月热力图 / 周趋势）**：只读「视图窗口」内的日志 + 全部计划版本（体积很小）。当前「从最早版本读到今天」在统计页是多余的，这是最便宜的收益。
2. **今日页**：每个习惯只需要「今日状态 + 当前连续」。当前连续从今天向前按块（如 60 天）读，遇到第一个「应做而未做」就停，典型情况只读 1 块。
3. **详情页**：单习惯全历史，只取 `(date, status)` 投影，一遍折叠算出当前/最长连续，不物化成实体列表。单习惯 10 年约 3600 行，不构成性能问题。

**为什么不用「最近 90 天」：** 连续超过 90 天的用户会看到被截断的数字，这是用户可见的正确性错误。

**为什么不加缓存/聚合：** 补打卡、撤销、改频率、归档恢复都会让缓存失效。「读时计算」的派生数据天然一致，别轻易放弃。

**先量：** 用 N1 的底座造 2 万行，测今日页冷加载耗时，设预算（例如 p95 ≤ 200ms，数字由你定）。
- 达标：只做第 1、3 项。
- 不达标：再做第 2 项。
- 仍不达标：才讨论缓存，并先写 ADR（重建方法 + 所有失效点）。

**domain 改动面很小：** `StreakCalculator` 接收「向后迭代的日志源」，规则代码不变，原 13 项单测继续有效。

**可落成任务：** `N7 benchmark 与预算`，之后重新定义 `TASK-023`。

### Q6 归档层级：展示层树，还是物理父表？

**结论：保留展示层树，这是你的需求中需要用户确认的一条，现在就去问。**

**怎么向用户解释：**
> 你要的是「按月/日浏览」，而不是「数据存两份」。
> 物理父子表会带来两个事实来源。归档/恢复要同时改两张表，日期边界出错时两边会对不上。而「按月/日分组」一条 `GROUP BY` 就能得到，视图层已经满足需求。

**第三种做法（归档快照文件）：** 不推荐用于 V1。归档的习惯仍可恢复，它仍属于数据库的一部分。快照文件会产生第二份副本，并与恢复语义冲突。如果用户真正的诉求是「历史永远保留、可以搬走」，那由 Q8 的导出满足（导出包含已归档习惯及其 `archived_on`）。

**需要同时写明的语义：** `archived_on` 是「最近一次归档日期」。归档→恢复→再归档会覆盖旧值。请让用户知晓并确认。

**可落成任务：** `N3` 一句话 ADR（决定：保持展示层，并解释「存储结构」的含义），随 Q9 的偏差 ADR 一起提交。

### Q7 提醒实现

**结论：以 `AlarmManager.setAndAllowWhileIdle` 为主，以 WorkManager 周期任务做「自愈」，不要反过来。**

**为什么不以 WorkManager 为主：** 周期任务最短 15 分钟，受 Doze 与待机桶影响，无法稳定锚定「21:30」，时间漂移会累积。

**推荐结构：**
- **单闹钟链**：全局只保留一个待触发闹钟，指向「所有习惯里最早的下一个提醒时刻」，触发后再重排。这样不会出现 N 个闹钟。
- **重排时机**：开机（`BOOT_COMPLETED`）、应用更新（`MY_PACKAGE_REPLACED`）、时间/时区变化、每次启动 App、每次修改提醒设置。
- **自愈**：WorkManager 每 6~12 小时跑一次，检查「应该已触发但今天还没发」的提醒。
- **补发策略**：只补**当天**、只补一次、只在习惯仍未完成时补；绝不补昨天的。用 `last_fired_date` 去重。
- **通知内容在触发时才查 DB 生成**，不要在排程时固化，避免「已完成还提醒」。
- **通知渠道**：一个「每日提醒」渠道。Android 13+ 的 `POST_NOTIFICATIONS` 在用户第一次打开提醒开关时请求，不要启动时就请求。被拒绝时，设置页显示「通知已关闭 → 去系统设置」，并在每次进入提醒页时检查渠道状态。
- **不申请精确闹钟权限**（你的约束）：对习惯类 App 也本就不符合 `USE_EXACT_ALARM` 的条件，正确。

**国产 ROM：**
- 把「上滑清除后台」当作可能等同强制停止，强制停止会清掉闹钟（AOSP 行为，OEM 更激进）。
- 在你的 iQOO 上实测：设 T+3 分钟的提醒 → 息屏 → 从最近任务划掉 → 观察是否到点；再做一次过夜。用 `adb shell dumpsys alarm | grep <包名>` 看闹钟是否登记，用 `adb shell cmd deviceidle force-idle` 模拟 Doze。
- 用 `ActivityManager.getHistoricalProcessExitReasons`（API 30+）记录「上次被系统杀」的原因，用于诊断。
- UI 文案按「尽力而为」措辞，别承诺准点。V1 不做前台服务（你的约束）是对的。
- 引导用户去系统电池/自启动设置，只给入口，不假设能自动解决。

**可测性：** 把 `nextReminderTime(now, 计划, 设置, zone)` 做成纯函数，用 JVM 单测覆盖（时区变化、今日已完成则不提醒等）。调度外壳保持很薄。Debug 构建加一个「5 秒后触发」入口。

**可落成任务：** `N5 提醒数据模型 ADR`（先做），`N9 F-012/013 实现`（030 之后）。

### Q8 备份导出（最小可用方案）

**结论：JSON + SAF `ACTION_CREATE_DOCUMENT`，导出全量；恢复只做「覆盖」，并拆分成两个任务。**

**格式：** JSON，单文件、多数组。
```json
{
  "format": "habit-tracker-backup",
  "format_version": 1,
  "app_version": "...",
  "exported_at": "2026-11-06T08:30:00Z",
  "habits": [],
  "schedule_versions": [],
  "logs": []
}
```
- `habits` 含已归档，`archived_on` 原样保存。
- 日期用 ISO-8601 字符串，不要用 epoch 毫秒表示纯日期。
- 从第一天起带 `format_version`，导入时容忍未知字段、拒绝更高版本。
- 为什么不选 `.db`：与版本耦合，直接复制运行中的数据库还有 WAL 未合并的风险。为什么不选 CSV：多表（计划版本）会有损，可以作为之后的附加导出，不是主格式。

**通道：** SAF，无需存储权限。恢复时用 `ACTION_OPEN_DOCUMENT`，MIME 用 `*/*`，由内容校验兜底，因为部分国产 ROM 的文件选择器会把 JSON 标成 `application/octet-stream`。

**隐私：** 导出包含完整日志，这是「数据搬得走」的含义，部分导出不叫备份。在导出界面明确提示「文件是未加密明文」，V1 不做加密。

**恢复 = 覆盖（V1 唯一方案）：**
1. 先把整份 JSON 解析并校验完（用与 DAO 相同的领域规则）。
2. 提示用户当前与备份的数量对比（习惯数、日志数、日期范围）。
3. **覆盖前自动导出当前数据**到 App 私有目录，保留最近 1 份，用于撤销。
4. 在**单个 `withTransaction`** 内「清空 → 插入全部」，任何失败整体回滚，原数据保持不变。
5. 为什么不做合并/只导入新习惯：ID 冲突、重复习惯、同日日志冲突、计划版本重叠，每一项都是独立的难题。

**关键测试：** 导出 → 清库 → 导入 → 再导出，两份文件逐字节相等（要求导出时排序规范化）。再放一份固定的 golden JSON 当格式契约，格式变更必须升 `format_version`。这个往返测试同时会检验触发器与事务，对 B3 很有价值。

**可落成任务：** `N4 030a 导出（只读，低风险）`、`N8 030b 恢复（依赖 N1）`。

### Q9 受保护文档：改 `REQUIREMENTS.md` 还是只记任务文件？

**结论：两者都要，按偏差类型分开处理。**

- **永久性/范围性偏差**（V1 不做提醒 UI、不做时长、不做图标/颜色编辑、不读动效缩放）：写**一份**偏差 ADR，并在 `REQUIREMENTS.md` 的每条需求上**加状态标注**（`V1 / 延后 / 取消`），不要改写需求原文。
- **暂时性偏差**（还没实现但仍计划实现，例如 F-012/013）：留在任务文件里，不动需求。

**为什么不能只记任务文件：** 评审时拿需求文档对照实现，会把每个偏差都当成缺陷，或者更糟，让偏差悄悄成为新的事实标准。

**一条原则：** 需求文档写「应该」，任务文件写「现在」，ADR 写「为什么偏离」。

**再加一张轻量追踪表** `project/DESIGN-DELTA.md`，一行一项：

| 设计稿元素 | 现状 | 原因 | 决定（延后/取消/待定） | 链接 ADR/任务 |
|---|---|---|---|---|

R1 评审可以直接拿它当检查清单。

**可落成任务：** `N3`（与 Q6 合并成一个 ADR + DESIGN-DELTA.md）。

### Q10 统计页周/年切换算不算 MVP 必须？

**结论：不算。** V1 保留「月热力图 + 周趋势」，周/年切换延后到 V1 之后。

**理由：** MVP 的成功标准是打卡、看见进度、数据不丢、有提醒。统计深度属于体验增强，优先级排在提醒与备份之后。年视图还会触发 B4 的窗口问题。

**一个细节：** 若切换控件已经渲染出来但不可用，请**隐藏它**。一个死控件比没有控件更伤体验。把周/年标到 DESIGN-DELTA 中。

## 3. 你漏掉的风险（按危害排序）

### R1 真机数据丢失路径（最高优先）
- **AGP 默认会在 `connected*AndroidTest` 结束后卸载被测 App 和测试 APK（请先确认）。** 如果你的手测数据就在这台 iQOO 的同一个包名下，一次设备测试就会把它清空。**跑 `TASK-026` 之前**：用 `adb exec-out run-as <包名> cat databases/<库名>` 备份当前 DB，或给设备测试单独配一个 `applicationIdSuffix`，把手测安装与测试安装分开。
- **签名一致性：** debug keystore 是机器私有的。换一台机器构建，覆盖安装会报签名不一致，只能卸载重装，数据随之丢失。请固定一个项目 keystore 并备份。
- **`allowBackup` / `data_extraction_rules`：** 产品承诺「无云同步」，但默认 Auto Backup 可能把 DB 上传到 Google 云。请明确设为不备份，或明确声明接受。反过来也要知道：关闭之后，卸载或清数据就等于丢失，应用内导出是唯一的搬迁路径。UI 上应提示这一点。
- 删除习惯的级联不可撤销，请确认有二次确认。

### R2 日期与「今天」的语义
- 注入 `Clock`。App 在前台跨过午夜时，今日页是否刷新（监听 `ACTION_DATE_CHANGED`）？
- 时区变化、用户手动改系统时间、旅行：日志日期应是「本地日历日」，时区变化后既有日志不迁移。连续天数只用 `LocalDate`，不用 `Instant`。
- 产品问题要用户决定：**日切点是 0 点还是凌晨 4 点？** 习惯类 App 里「凌晨打卡算前一天」很常见。
- 周起始日：统计周趋势、详情页本周、计划里的「每周」必须用同一个定义（固定周一，或按 locale 的 `WeekFields`），不要三处各算各的。
- 测试夹具：跨年、闰日、跨周、跨月。

### R3 「归档期间」应当是未计划，而不是漏打（需确认）
归档→10 天后恢复。这 10 天在连续天数里算「应做未做」（连续被打断），还是「未计划」（不影响）？B6 的造数里请专门加这一条，并让今日 / 统计 / 详情三处一致。同理：已归档习惯的历史是否计入统计，需要一个明确的产品语义。

### R4 迁移与 schema 决策窗口
- 目前 schema 还是 v1。**任何你想改的东西（提醒表、`duration_seconds`、归档字段）趁现在都还是「v1 修订」，不需要迁移。** 一旦你自己的真机里有长期数据，每次改 schema 都变成迁移。
- 提醒必然要持久化，且备份必须包含它，所以 N5 要先于备份格式定稿。
- 第一次真迁移之前，把 `MigrationTestHelper` 的测试模板建好。

### R5 Android 15 强制 edge-to-edge 与系统深色
- 若使用 `enableEdgeToEdge()` 的默认 `SystemBarStyle.auto`，在**系统深色**而 App 强制浅色时，状态栏图标可能变白，落在浅色背景上看不见（取决于你的系统栏外观如何设置，需确认）。请在 iQOO 上打开系统深色模式，截一张图看看。
- IME 弹出时数值输入框是否被遮住。
- 字体缩放 1.3~2.0 下的布局。
- 国产 ROM 的「智能反色/强制深色」是否会改写你的浅色界面。
- 这几项适合作为手测清单，不必全部自动化。

### R6 Release 构建从未验证
`verify-all` 只有 `assembleDebug`。请加入 `assembleRelease`（R8/资源压缩）和 `lint`，二者都可能在 release 才暴露问题。若 lint 被沙箱阻断，就在文档里记为已知缺口。

### R7 单测同源自证
154 个单测由实现作者写，存在「测试和实现共享同一个误解」的可能。变异抽查（Q1 第 3 点）是最便宜的缓解办法。

### R8 并发与幂等
- 快速双击打卡：写入是否幂等（唯一键 / upsert）？
- Presenter 的乱序加载：慢的旧请求晚于快的新请求返回，会覆盖新状态。请确认使用了 `collectLatest` / `flatMapLatest`，或等价手段（需确认）。
- Presenter 的生命周期归谁？旋转和进程重建后是否保留？这属于 Q2 L2 的第 2 条。

### R9 依赖供应链
腾讯镜像 → 启用 Gradle dependency verification；版本用 version catalog 固定。

### R10 代码本身的单点
文档没有提到远端仓库。若只在 `D:\` 本地，一次磁盘故障就是全部丢失。请确认有私有远端或定期 `git bundle`。

### R11 国产 ROM 小细节（合并列出）
- 文件选择器 MIME 标记不可靠（见 Q8）。
- 新装 App 的通知可能默认被静音或关闭。
- 划掉后台可能清闹钟（见 Q7）。
- 可以用 `getHistoricalProcessExitReasons` 辅助诊断。
- 无障碍：热力图只靠颜色传达信息，对色盲和 TalkBack 不友好，建议加数值或形状冗余。
- 「减弱动效」可读 `Settings.Global.ANIMATOR_DURATION_SCALE`，一个很小的任务，P3。
