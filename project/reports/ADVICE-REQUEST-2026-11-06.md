- 产品：本地优先的单机习惯追踪 App；无账号、无服务器、无云同步；V1 不做深色模式/小组件/前台服务。
- 技术：单 `:app` 模块，Kotlin + Jetpack Compose + Material 3，Room schema v1（4 表），minSdk 26 / targetSdk 35，强制 edge-to-edge。
- 架构：domain 纯规则（Schedule/Streak/Habit/LogStatus）→ repository 接口 → Room 实现 → Presenter（纯 Kotlin + StateFlow）→ Compose 页面；UseCase 层收口写入规则。
- 当前阶段：`Gate 3`。已有页面：今日、新建、统计、我的（归档/恢复）、习惯详情。全部接真实数据。
- 治理：`tools/verify-all.ps1` = 治理检查 22 项 + 单测 154 项 + `verify-schema.mjs` 40 项 + `verify-dao.mjs` 38 项 + `assembleDebug` + `git diff --check`。最近一次全绿（exit 0）。
- 真机：iQOO Neo7 SE（Android 15），USB 调试；`connectedDebugAndroidTest` 通道可用（已用 1 个 SmokeTest 证明）。
- 测试限制：本机沙箱禁止 Gradle 测试 worker 管道，`gradlew test` 必失败；纯 JVM 测试由 `tools/run-unit-tests.ps1` 直接跑 JUnit。无模拟器（无 WHPX）。

## 3. 瓶颈（按我判断的严重度排序）

### B1 评审债：7 个 `IMPLEMENTED`，里程碑未定义
- 现状：功能持续叠加，评审一直后置；`project/reviews/` 只有早期 4 份。
- 风险：设计与实现的偏差（见 B5、B6）无人复核；`main` 上的「可交付」状态没有独立证据；一旦评审开始，改动面已经很大。
- 我的倾向：先做一轮批量评审（把 7 个任务打包成 1 个 Review），再继续功能；但这会消耗若干轮对话预算。

### B2 测试金字塔倒置：154 个 JVM 单测，UI 全靠手测
- Presenter/规则覆盖较好；Compose 渲染、手势、导航参数、状态恢复**零自动化**。
- 设备侧只跑了 1 个 `SmokeTest`（断言包名），不构成回归保护。
- `gradlew test` 不可用 → Robolectric 也走 Gradle worker，**推测**同样会被沙箱阻断。
- 每次 UI 改动都要装 APK + 手动点 + 截图，成本高且不可重复。

### B3 Room 运行时契约没有自动化证据（`TASK-004` `PARTIAL`、`TASK-026` 未开始）
- 已验证：schema 文本、约束的等价 SQL、DAO 语句语义（`node:sqlite`，40 + 38 项）。
- **未验证**：Room 打开数据库时 `DatabaseConstraints.callback()` 是否真的注册了触发器；实体/Converter 往返；`withTransaction` 原子性；`Flow` 失效通知。
- 这意味着「数据库保证不变量」这条结论目前只有 SQL 层证据，没有运行时证据。

### B4 日志读取窗口没有收敛（`TASK-023` 未做）
- 今日页批量读、统计页、详情页都从「最早计划版本」读到今天；习惯多、年数长时线性增长（计划里估 20 习惯 × 3 年 ≈ 2 万行/次）。
- 详情页我为了连续天数正确，明确用「全历史」窗口；这是正确性优先的取舍，但把性能问题放大了。
- 统计/详情都是全量内存计算，没有分页或聚合表。

### B5 设计稿里有、数据里没有的控件
- 提醒（`F-012/013`）：设计稿的「每天 21:30 提醒」、详情页计划行铃铛——**没实现**，详情页我删掉了铃铛与时间。
- 时长（`duration_seconds`）：设计稿统计卡「每次平均 22 分钟」——字段存在但**从未写入**，详情页我改成「本月次数」。
- 编辑图标/颜色：`UpdateHabitUseCase` 只改名称/目标/单位，详情页编辑弹窗遵循同一范围。
- 减弱动效：设计稿有 `prefers-reduced-motion`，Android 侧未读 `ANIMATOR_DURATION_SCALE`。

### B6 真机数据单薄
- 每个测试习惯的计划都从「当天」生效 → 近 5 周网格真机上只出现过今天一格；「未计划日」「未来日」只有单测证据。
- 未造数验证：跨周/跨月边界、多计划版本（改频率）、带日志习惯的级联删除。
- 归档分组只有「单月单日」真机数据。

### B7 「归档按月/日父子级」是展示层，不是物理层级
- 用户要求「归档后的习惯存储结构为月份/日期的父子级」；当前实现是读取 `archived_on` 后在 UI 建树（`ArchiveGroups`），数据库仍是单表 + 单一日期列。
- `DATABASE.md` 8.3 明确 `archived_on` 是归档事实的**单一来源**；真要建父子表需要 ADR + 迁移（且会引入冗余与不一致风险）。
- 我的判断：展示层足够满足「按月/日浏览」，但这是一个**需要用户确认**的语义决定。

### B8 环境与依赖
- 依赖走腾讯 Maven 镜像；SDK 许可文件由 AI 代写（等同代用户接受条款）——需要用户复核。
- 无模拟器；真机手动验证依赖设备在线与解锁。

## 4. 开放问题（请逐条给建议；括号是我的倾向）

**Q1 流程**：现在应该「先补 7 个任务的批量评审」，还是「先做 `TASK-030`（备份+巡检）把 MVP 收口，再一次性评审」？（我倾向先评审，因为偏差会累积；但评审需要逐任务读 diff，成本高。）

**Q2 UI 自动化路线**：三条路——
- (a) 设备侧 Compose UI 测试（`createAndroidComposeRule`）跑在真机上，覆盖 5 条主路径；
- (b) Robolectric（**推测**被沙箱 worker 禁）；
- (c) 截图对比（无基准库，维护成本高）。
你推荐哪条？若 (a)，最小用例集怎么切，才不至于变成「点一遍的脚本」？

**Q3 Room 契约测试（`TASK-026`）最小集**：如果只能写 4 个设备侧用例，你会选哪 4 个？（我的候选：触发器注册、Converter 往返、`withTransaction` 回滚、`Flow` 收到变更。）

**Q4 日志窗口**：在「不加聚合表」的前提下，怎样把读取收敛到有界窗口又不破坏连续天数？（按版本分段 + 只读最近 N 天 + 连续天数缓存？还是先加「最近 90 天」窗口并把「最长连续」交给一次性聚合？）

**Q5 详情页第三张卡**：保留「本月次数」，还是给 `duration_seconds` 补写入与 schema v2（`TASK-010` 的 DAO 校验也要跟着改）以还原设计稿「每次平均」？

**Q6 归档层级**：展示层树 vs 物理「月/日」父表——你会怎么向用户解释取舍？有没有第三种做法（例如生成归档快照文件）？

**Q7 提醒实现**：约束是「Normal 精度、允许延迟、不申请精确闹钟权限」。
- `WorkManager` 周期任务（最短 15 分钟）→ 简单但时间漂移大；
- `AlarmManager.setAndAllowWhileIdle`（不申请 `SCHEDULE_EXACT_ALARM`）→ 更接近「21:30」但仍可能延迟；
- 国产 ROM 后台限制是主要风险。
你推荐哪条？通知渠道与「错过当天提醒」的补发策略怎么定？

**Q8 备份导出**：`TASK-030` 要求「数据搬得走」。
- 格式：JSON（可读、可迁移）vs CSV（表格友好）vs 直接复制 `.db`（完整但不可读、版本耦合）；
- 通道：SAF `ACTION_CREATE_DOCUMENT`（无存储权限）vs MediaStore；
- 恢复：覆盖 vs 合并 vs 只导入新习惯；
- 隐私：导出文件里是否包含完整日志。
你的最小可用方案是什么？

**Q9 受保护文档**：详情页为了不造假数据删了提醒行、换了统计卡，这类「设计稿 vs 数据现实」的偏差，应该改 `REQUIREMENTS.md`（需 ADR）还是只记在任务文件里？

**Q10 范围**：统计页的周/年切换（`TASK-031` 已知缺口）算不算 MVP 必须？还是留到 V1 之后？
